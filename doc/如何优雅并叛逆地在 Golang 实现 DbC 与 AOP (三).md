# 如何优雅并叛逆地在 Golang 实现 DbC 与 AOP (三) — 影子坍缩与生态兼容

> 引擎仓库：[github.com/imnive-design/inco](https://github.com/imnive-design/inco)

## 一、本体论：方言

Inco 不是 Go 的扩展，是 Go 的**方言**。

这个定位很重要。扩展意味着向语言添加能力——新关键字、新语法、新运行时。方言意味着在语言的合法边界内，用不同的方式表达相同的语义。

`// @inco: x != nil` 是合法的 Go 注释。任何 Go 工具链都能编译包含它的文件。它不会在 `go build` 时报错，不会让 `gopls` 崩溃，不会让 `go vet` 产生警告。

但它有额外的语义——只有 Inco 引擎能理解。

这就是方言的特征：**对不懂它的人，它是噪音；对懂它的人，它是信号。**

方言的代价也很明确：**依赖翻译**。如果接收方不装 Inco，那些注释就只是注释——守卫不存在，前置条件不生效。代码在语法上正确，但在语义上不完整。

## 二、坍缩流程

解决方案是**坍缩**——把方言翻译回通用语。

`inco release` 做的事情：

```
foo.inco.go  →  foo.go   (影子内容，含 if 守卫)
             →  foo.inco (原始源文件备份)
```

### 2.1 具体步骤

1. **读取 overlay**：从 `.inco_cache/overlay.json` 获取源文件到影子文件的映射。
2. **筛选 `.inco.go`**：只处理 `.inco.go` 结尾的文件，普通 `.go` 跳过。
3. **写入 `.go`**：将影子文件内容（含守卫代码）写为 `foo.go`，头部加上 `// Code generated by inco. DO NOT EDIT.`。
4. **备份原始文件**：`foo.inco.go` → `foo.inco`。

完成后，目录中只有标准 `.go` 文件。`go build ./...` 直接编译，不需要 `-overlay`，不需要 Inco。

### 2.2 生成文件标记

写入的 `.go` 文件以标准的 generated-code header 开头：

```go
// Code generated by inco. DO NOT EDIT.
```

这是 Go 生态的通用约定（`go generate`、protobuf、stringer 都用同样的格式）。效果：

- `goimports` 不会修改它。
- `golangci-lint` 默认跳过它。
- Inco 自身的 `gen` 和 `audit` 也会识别并跳过。

### 2.3 `//line` 不删除

坍缩后的 `.go` 文件保留 `//line` 指令。这意味着即使用 `go build`（不带 overlay）编译，panic 堆栈仍然指向原始 `.inco.go` 的行号。

这是有意为之。发布后的代码虽然脱离了 Inco，但调试信息仍然指向开发态的源文件——对维护者来说，知道守卫来自哪一行比知道它在生成文件的哪一行更有用。

### 2.4 恢复

```bash
inco release clean .
```

逆操作：删除生成的 `.go` 文件，将 `.inco` 重命名回 `.inco.go`。一切回到开发态。

## 三、扩展名协议

三种状态，三种扩展名：

| 扩展名 | 状态 | 编译器行为 | 含义 |
|--------|------|-----------|------|
| `.inco.go` | 开发态 | 正常编译（通过 overlay 注入守卫） | 源文件，含 `@inco:` 指令 |
| `.go` | 发布态 | 正常编译 | 守卫已硬化为 `if` 语句 |
| `.inco` | 存档态 | **不编译** | 原始源文件备份 |

### 一点野心

如果抛开现实约束，`.inco` 才是最纯正的开发态扩展名——它声明了"这个文件包含 Inco 方言"，身份清晰，没有多余的后缀。

但现实是 Go 工具链只认 `.go`。`gopls` 不分析非 `.go` 文件，`go vet` 不检查它们，IDE 的语法高亮、跳转定义、自动补全全部失效。开发态需要这些能力，所以开发态文件必须是 `.go` 结尾。

`.inco.go` 是一个妥协：`.go` 后缀让 Go 工具链正常工作，`.inco` 前缀标记方言身份。它不纯粹，但实用。

而 `.inco` 作为存档态扩展名反而恰如其分：存档态不需要编译，不需要 LSP，不需要任何工具链支持——它只需要一个身份标记，和一个"编译器不会碰我"的保证。

### `.inco` 的安全性

`.inco` 不是 `.go`。Go 编译器只编译 `.go` 结尾的文件。

这不是约定，是**编译器级约束**。你不可能意外地把一个 `.inco` 文件编译进二进制——除非你手动改扩展名。

这个特性防止了最危险的静默失效场景：

```
// 灾难场景（不会发生）：
// 1. 开发者执行 release
// 2. foo.inco.go → foo.inco (备份)
// 3. foo.go (带守卫) 生成
// 4. 某人把 foo.inco 改回 foo.inco.go
// 5. 现在目录里有 foo.inco.go 和 foo.go —— 两个文件定义同一个包的同一组函数
// 6. go build 报错：redeclared in this block
```

编译器本身就是安全锁。重复定义会被立即拒绝，不存在"两份代码静默共存"的可能。

### 语义硬化

"硬化"这个词是精确的。

开发态的 `// @inco: x != nil` 是柔性的——它是注释，删掉不影响编译。引擎不就位，守卫不存在。

坍缩后的 `if !(x != nil) { panic(...) }` 是刚性的——它是代码，删掉影响行为。不依赖任何引擎，直接由编译器执行。

从柔到刚，从注释到代码，从方言到通用语。这就是坍缩。

## 四、生态兼容

### 零依赖分发

坍缩后的项目：

- **`go.mod`**：不包含 Inco 依赖（Inco 是开发工具，从来不在 `go.mod` 里）。
- **`import`**：影子文件的 import 已由引擎注入，不需要手动处理。
- **构建**：`go build ./...`，标准命令，无特殊 flag。

接收方看到的是一个普通的 Go 项目。唯一的痕迹是 `// Code generated by inco. DO NOT EDIT.` 和 `//line` 指令——前者是 Go 生态的标准做法，后者是编译器内建机制。

### 双态工作流

开发态和发布态可以在同一个仓库中切换：

```bash
# 开发：用 inco 工具链
inco build ./...
inco test ./...

# 发布：坍缩
inco release .

# 现在是标准 Go 项目
go build ./...
go test ./...

# 恢复开发态
inco release clean .
```

`inco release --dry-run .` 可以预览坍缩结果而不修改任何文件。

### CI 分支策略

更进一步：用 CI 在同一个仓库中维护开发态和发布态两个分支。

```
main   ← 发布态（标准 Go，go build 直接编译）
dev    ← 开发态（.inco.go，需要 inco 工具链）
```

CI 流程：

1. 开发者在 `dev` 分支提交 `.inco.go` 源文件。
2. CI 执行 `inco release .`，生成坍缩后的标准 Go 代码。
3. 将坍缩结果提交到 `main` 分支。

`main` 分支永远是可直接 `go build` 的标准 Go 项目。`dev` 分支永远是开发态。两个分支共存于同一仓库，通过 CI 自动同步。

消费者 `go get` 拉到的是 `main`——标准 Go，零依赖。贡献者 clone 后切到 `dev`——完整的 Inco 开发体验。

#### GitHub Actions 示例

完整的 CI workflow（参见 `.github/workflows/release-single-repo.yml`）：

```yaml
name: Release inco → main

on:
  push:
    branches: [inco]

permissions:
  contents: write

jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout inco branch
        uses: actions/checkout@v4
        with:
          ref: inco

      - name: Setup Go
        uses: actions/setup-go@v5
        with:
          go-version-file: go.mod

      - name: Install inco
        run: go install github.com/imnive-design/inco-go/cmd/inco@latest

      - name: Release
        run: |
          inco release .

          # Rename remaining .inco.go files (those without directives) → .go
          find . -name '*.inco.go' -not -path './.inco_cache/*' | while read -r f; do
            target="${f%.inco.go}.go"
            mv "$f" "$target"
          done

          rm -rf .inco_cache

      - name: Push to main
        run: |
          git config user.name  "github-actions[bot]"
          git config user.email "github-actions[bot]@users.noreply.github.com"
          git add -A
          git commit -m "release: inco@${GITHUB_SHA::7}" --allow-empty
          git push origin HEAD:main --force
```

推送到 `inco` 分支时，CI 自动坍缩并 force-push 到 `main`。`main` 永远是干净的标准 Go 代码。

### 自举验证

Inco 自身就是用 `.inco.go` 写的。引擎的源码中充满了 `@inco:` 指令：

```go
// engine.inco.go
func (e *Engine) Run() error {
    // @inco: e != nil, -return(fmt.Errorf("Run: nil engine"))
    // @inco: e.Root != "", -return(fmt.Errorf("Run: root must not be empty"))
    ...
}

// release.inco.go
func Release(root string, dryRun bool) error {
    // @inco: root != "", -return(fmt.Errorf("Release: root must not be empty"))
    ...
}
```

这意味着 `inco release .` 可以把 Inco 自身坍缩为标准 Go 代码。一个用自己方言写的翻译器，能把自己翻译成通用语。

这是最严格的兼容性验证——如果坍缩后的代码不能正确编译和运行，引擎本身就会失效。

## 五、未解决的问题

坍缩解决了分发——接收方拿到标准 Go，不需要知道 Inco 的存在。生态兼容验证通过——自举、CI 双分支、零依赖构建，所有出口都是通的。

但这些都是**出口**的问题。入口呢？

开发者每天面对的不是坍缩后的 `.go`，而是开发态的 `.inco.go`。在这个状态下，`@inco:` 指令是注释——gopls 不认识它，IDE 不高亮它，写错了没人报错。方言的分发问题解决了，方言的**可见性**问题还在。

一个没有语法高亮、没有错误提示、没有悬停预览的方言，写起来全靠记忆和纪律。这不够。
